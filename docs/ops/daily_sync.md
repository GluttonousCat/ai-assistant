# 行情定时更新

> 更新：2026-11-17。盘后调度 `jobs/scheduler.py`，盘中调度 `jobs/intraday_scheduler.py`。

## 一、系统设计

另有独立的60F观察任务：交易日四根原生60F于10:30、11:30、14:00、15:00收盘，
留120秒等待网页源落地，**10:32、11:32、14:02、15:02 Asia/Shanghai**开始采集并扫描。
时间是任务触发时间，全池请求与计算完成后才原子展示，不承诺整点全部可见。
只取截至本轮的完整前缀（1/2/3/4根）；原始分钟与当天真实因子入库，
不推进盘后完整日检查点。日K背景始终使用此前完整交易日，盘中评分及名单保持独立。

后端 lifespan 启动常驻 asyncio 任务，在**交易日17:00 Asia/Shanghai**顺序执行：

1. 获取当前非ST上市名单，沿用看板已纳入的北交所股票；排除目标日尚未上市的股票。
2. Tushare 日K、日度指标、真实复权因子按最近5个交易日重叠 upsert；停机较久时从较早的数据截止次日回补。
3. 对照本地实际有成交的日K逐股检查原生60F，每交易日应有10:30、11:30、14:00、15:00四根；仅抓缺失股票，最多4个并发。
4. 检查缺根、非法时点、日K/因子关联，核验通过后沿用**已发布快照的策略参数**重算全池，原子发布新快照。
5. 继续既有财务公告、分红和披露日期增量流程。

全部数据库和外部IO在线程中执行；HTTP行情接口仅查询本地库。管理员手动更新接口只排队后台任务，不等待分钟采集。
共享的操作系统文件锁防止CLI与服务同时更新；进程退出自动释放锁，遗留锁文件不会阻止恢复。
失败保留上一版快照，已入库的正确股票不回滚、不重复全量下载。正常任务失败后每30分钟重试，最多额外3次；
后续交易日和下次服务启动继续检查。`schedule.enabled=false`关闭定时任务，配置改动需重启。

## 二、需求优化

盘中四轮共用当天固定的股票池及盘前策略来源；即使17点后重启，也从此前日快照取母背景。
启动只补当天最新到期的一轮，已完成轮次不重采、不重算；失败保留断点，5分钟后重试，
每轮最多3次尝试，新时点到期后优先最新轮次。OS锁覆盖采集到发布全流程，避免多进程并发冲击免费源。
页面每分钟检查盘中结果，计算期间展示上轮成功名单和本轮进度；不增加盘中邮件。

同时区分“已经入库”和“已经展示”。看板提供日K入库、60F入库、已发布快照三种日期及任务阶段。
前端每60秒轻量查询状态，页面隐藏时不轮询；出现新run_id才重新读取全池快照，恢复可见时立即检查。
策略版本提示与行情新鲜度分开表述，不再把“沿用旧规则”写成“旧快照”；定时更新不自动启用新版策略。
库内最大日期只表示存在该日期记录，完整性以逐股审计为准。盘中不把当天当作已到期的盘后数据；周末不生成K线。

Tushare说明日线通常在15–16点入库，日度指标在15–17点更新；17点是项目触发时刻，供应商延迟由失败重试处理。
资料：[日线接口](https://tushare.pro/document/2?doc_id=27)、[日度指标](https://tushare.pro/document/2?doc_id=32)。
新浪原生分钟使用现有同源滚动历史接口，不补造缺根、不混用其他源、不伪造复权因子。

## 三、问题

| 历史问题 | 根因 | 处理 |
|---|---|---|
| 盘中观察只有一次午间手工结果 | 没有后端四时点调度 | 收盘后120秒采集、串行扫描、持久回执及启动最新轮次补漏 |
| 晚启动可能拿到当天盘后日K作盘中背景 | 每轮临时读取最新正式快照 | 当天共用固定来源；首次晚启动按当天零点以前查源快照 |
| 旧时点重跑盖掉新结果 | 无发布时间顺序保护 | 发布锁内比较as_of；每轮归档，latest只前进 |
| 定时采集晚于用户需求 | 原默认21点 | 统一为交易日上海时间17点 |
| 宿主机换时区改变执行时刻 | 使用系统本地时区 | 统一Asia/Shanghai，外部UTC先转换 |
| 17点前补漏错误拉取当天 | 旧逻辑固定16点作为到期时刻 | 按配置时分确定最近应有交易日 |
| 补漏检查阻塞HTTP | async中直接查询PG | 仓储/工具收敛与to_thread |
| 日K已到13日、60F与看板仍在12日 | 17点任务只采日线；启动仅看daily最大日期 | 衔接日K→60F→原子发布；启动检查三者与成功审计状态 |
| 宣称回补5日却没补到旧日遗漏 | 最大日期断点直接跳过已有区间 | 新增显式resume=False，定时重叠回补，历史长批任务仍保留默认续传 |
| 新股、摘帽及既有北交所股票日K漏采 | 旧stock_basic缓存与分钟池不一致 | 刷新当前非ST名单，并将同一显式股票池传给日线采集；不再被旧缓存二次过滤 |
| 接口有返回就误判最新 | 非空响应可能只含旧K线 | 入库后再按股票/交易日核对四根与时点；审计失败不推进快照 |
| 暂时网络异常空等到下个交易日 | 调度缺少日内重试 | 30分钟重试，最多额外3次，逐股已有数据复用 |

## 四、处理方案

盘中配置：`intraday_watch.enabled`默认true、`workers`默认4（1—4）；
环境变量`INTRADAY_WATCH_ENABLED=false`可单独关闭，修改后重启生效。
进度及回执在`output/market/intraday_watch/scheduler.json`和`<日期_HHMM>/scheduled.json`，
当天来源固定在`<日期>/session.json`。管理员调度状态增加`intraday_watch`，普通盘中接口附带去敏进度。
`cache_intraday_prefix --cutoff`和`scan_intraday_watch --cutoff`均支持四时点，
静态PNG只在扫描CLI显式传`--render-static`时额外导出；自动链路直接供应可拖拽K线，减少发布等待。
17点完整刷新和18点邮件保持原流程。

启动自检：比较应有交易日、库内日K/因子/60F截止与快照，同时要求已有完整任务状态。
13日是周五，14/15日是周末；16日17点前应有日期是13日。无成功状态或数据滞后即补漏，不抓启动财务。
目标日日线缺失须由Tushare全天停牌记录解释，不能自行把无数据认定停牌；因子缺失直接中止。
停牌豁免仅接受S记录且日内停牌时段为空，依据[每日停复牌接口字段说明](https://tushare.pro/document/2?doc_id=214)，日内停牌不豁免全天四根核验。
日度指标缺失标为partial并重试。分钟审计按真实daily成交日判断，不给停牌日补造K线。

进度文件：`output/market/refresh/status.json`，审计：`output/market/refresh/<目标日期>_audit.json`。
快照仍写入原有仓储与`output/market/trend/`；不更改冻结量化研究、历史回测或策略默认参数。
管理员接口`GET /admin/scheduler-status`返回运行、下一执行/重试时间及最近结果；
`POST /admin/sync-today`返回queued或busy，沿用DB实时管理员校验。
普通行情页通过`GET /api/v1/market/freshness`读取进度，仍需JWT，不返回内部异常与部署信息。

手动补漏：`.venv/Scripts/python.exe -m jobs.refresh_market --end 2026-11-13`。
`--skip-quotes`只用于日K与因子已核验入库的分钟补漏，仍会核验实际完整性。
服务常驻才能按时触发，离线期间靠下次启动补漏；采集或计算期间继续提供上一版可用快照。
