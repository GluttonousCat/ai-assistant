# 日线定时采集

> 更新：2026-11-12。代码 `jobs/scheduler.py`，配置 `config.yaml schedule`。

## 一、系统设计

后端lifespan启动常驻asyncio任务，在**交易日17:00 Asia/Shanghai**执行既有增量管线。
该时区独立于宿主机时区；非交易日不抓不存在的当日日线，下一次时间直接顺延到交易日。
`schedule.enabled=false`可关闭；调度时间为`sync_hour=17, sync_minute=0`，改动后重启后端生效。

任务同步daily/daily_basic/adj_factor，并保留既有财务公告、分红和披露日期增量流程。
过去5个交易日重叠回补、数据库upsert与原有异常日志保留。17:00任务不包含60F外部采集或全池筛选。

## 二、需求优化

由原21:00提前至17:00。Tushare官方说明日线通常在15–16点入库，日度指标在15–17点更新；
17点是本项目选择的触发时间，不是供应商完整性承诺。
资料：[日线接口](https://tushare.pro/document/2?doc_id=27)、[日度指标](https://tushare.pro/document/2?doc_id=32)。
重叠回补继续覆盖后续修订或迟到记录，不把空结果伪造成成功数据。

## 三、问题

| 历史问题 | 根因 | 处理 |
|---|---|---|
| 定时采集晚于用户需求 | 配置与回退默认都是21点 | 配置、默认、启动日志和文档统一为17点 |
| 宿主机换时区会改变真实执行时刻 | datetime.now使用系统本地时间 | 计算与记录统一使用Asia/Shanghai，外部传入UTC会先转换 |
| 重启补漏在目标时刻前拉当天数据 | 旧逻辑固定16点起认定当天应齐 | 按配置时分判断当天是否到期，17点前只检查上一交易日 |
| 补漏检查可能阻塞HTTP | PG最大日期查询直接在async函数里执行 | 仓储/工具收敛，asyncio.to_thread隔离数据库IO |
| 意外异常会结束长期调度任务 | 定时循环外层缺少保护 | 记录异常并保留下一交易日任务 |

## 四、处理方案

启动时先比较应有交易日与库内daily最新日期，发现缺口即补行情，不跑启动财务抓取。
17点之后启动可补当天，17点前启动先补上一交易日；随后等待下一次17点。
健康检查只检查最大日期，不宣称覆盖逐股/逐日完整性；分钟对应的因子缺口由独立修复任务检查。

管理员接口`GET /admin/scheduler-status`返回running、last_run、last_result、next_run与time_zone，
`POST /admin/sync-today`可手动触发。沿用既有管理员实时角色校验。
服务需要常驻才能在17点触发；服务离线期间由下次启动补漏兜底。
